## Work Log

### 1. Stripe Recurring Billing (auto-charge on renewal)

**`prisma/schema.prisma`** — Added 5 new fields to the `Subscription` model:
- `stripeCustomerId String?` — Stripe Customer object id (`cus_xxx`); reused across cycles.
- `stripeSubscriptionId String?` — Stripe Subscription object id (`sub_xxx`); webhook matches renewals back to our row.
- `stripeStatus String?` — mirrors Stripe's own status (`active` / `past_due` / `canceled` / `incomplete`); lets the /billing page show "Auto-renew: ON" without an extra Stripe API call.
- `stripeCurrentPeriodEnd DateTime?` — Stripe's `current_period_end`; stamped by the webhook → "Next charge: Nov 6, 2026" UI.
- `dunningAttempt Int @default(0)` — counts failed renewal attempts (see dunning section).

`npx prisma validate` → "valid 🚀". Prisma client was regenerated by the project's auto-regen hook; confirmed `generated/models/Subscription.ts` carries the new fields.

**`src/lib/stripe.ts`** — Added 3 helpers:
- `findOrCreateStripeCustomer({ email, name, internalCustomerId })` — looks up an existing Stripe Customer by email (`stripe.customers.list({ email })`) and mints a new one if none exists. Guarantees each tenant reuses the same Stripe Customer across cycles, dunning retries, and Customer Portal sessions.
- `createStripeSubscription({ customerId, stripeCustomerId, priceAmount, currency, interval, subscriptionId, planName })` — creates a one-off Stripe `Product` + recurring `Price` + `Subscription` wired to the customer, with `payment_behavior: "default_incomplete"` + `payment_settings.save_default_payment_method: "on_subscription"`. The internal `customerId` + `subscriptionId` are stamped onto the Subscription's metadata so webhook events can reconcile without a lookup table. Returns `{ stripeSubscriptionId, clientSecret }` — the `clientSecret` is the first invoice's PaymentIntent secret (for Stripe Elements).
- `createCustomerPortalSession({ stripeCustomerId, returnUrl })` — opens a Stripe Customer Portal session so the user can update their card, swap plans, view past invoices, and cancel — all on Stripe's PCI-DSS-compliant surface.

**`src/app/api/stripe/create-subscription/route.ts`** (new) — POST + GET handlers:
- **POST** — auth-required; resolves the internal Subscription row (existing or freshly-created), looks up the Customer by email + name, calls `findOrCreateStripeCustomer` → `createStripeSubscription`, stamps `stripeCustomerId` + `stripeSubscriptionId` + `stripeStatus="incomplete"` on the internal row, audits the action, and returns `{ ok, stripeSubscriptionId, stripeCustomerId, clientSecret, subscriptionId }`.
- **GET** (`?portal=true`) — auth-required; resolves the caller's most-recent Subscription with a Stripe Customer id, calls `createCustomerPortalSession`, returns `{ url }` for the browser to redirect to.

**`src/app/api/stripe/webhook/route.ts`** (modified) — added 2 new event handlers:
- **`invoice.paid`** → `handleInvoicePaid`:
  1. Resolves the internal Subscription via `resolveSubscriptionFromInvoice` (looks up by `stripeSubscriptionId`, falls back to the Stripe Subscription's metadata `internalSubscriptionId`, then to `internalCustomerId` → most-recent sub).
  2. Stamps `stripeStatus="active"` + `stripeCurrentPeriodEnd` (from `invoice.period_end`) on the internal row.
  3. Resets `dunningAttempt` to 0 (the renewal succeeded, so the prior dunning sequence is no longer relevant).
  4. Idempotency check on `transactionId = invoice.id` — if a Payment row already exists, skip the side effects.
  5. Creates a completed Payment row (with card `last4` + `brand` from the charge, linked to the owner's default BankAccount).
  6. Generates a paid Invoice row (idempotent on the `subscription:<id>|payment:<id>` fingerprint — same pattern as `/api/payments` POST).
  7. Fires a `"Monthly payment received"` (or "Yearly") notification to every tenant user — `type="payment_received"`, `sendEmail=true`.

- **`invoice.payment_failed`** → `handleInvoicePaymentFailed`:
  1. Resolves the internal Subscription (same path as `invoice.paid`).
  2. Records a failed Payment row (idempotent on the Stripe invoice id — Stripe retries on the same invoice would otherwise create duplicate failed Payment rows).
  3. Reads `invoice.attempt_count` (Stripe's 1-indexed retry counter) and hands off to `handlePaymentFailure()` (dunning module).

**`src/app/billing/page.tsx`** (modified) — `CurrentPlanCard` now surfaces:
- **"Auto-renew: ON"** emerald badge when a Stripe subscription exists and is `active` (not `past_due` or `canceled`).
- **"Payment past due"** amber badge when `stripeStatus === "past_due"`.
- **"Auto-renew: OFF"** rose badge when the Stripe subscription is `canceled` (auto-renew has been turned off by dunning).
- **"Next charge: Nov 6, 2026"** card — pulls the date from `stripeCurrentPeriodEnd` (set by the webhook). Card turns amber + shows "Payment failed — attempt N. Update your card via 'Manage billing'." when past_due.
- **"Manage billing"** button — calls `GET /api/stripe/create-subscription?portal=true` to open the Stripe Customer Portal in a full-page redirect (where the user can update their card, swap plans, view past invoices, cancel).
- Falls back to the legacy "Next billing" card (computed from `startDate + cycleDays`) when no Stripe subscription exists, when `stripeCurrentPeriodEnd` is null, or when the subscription has been cancelled.

**`src/app/api/subscriptions/route.ts`** (modified) — GET response now includes `stripeCustomerId`, `stripeSubscriptionId`, `stripeStatus`, `stripeCurrentPeriodEnd`, `dunningAttempt` so the /billing page can render the new UI without an extra API round-trip.

### 2. Dunning / Payment Failure Handling

**`src/lib/dunning.ts`** (new) — exports `handlePaymentFailure(subscriptionId, attempt)` + `MAX_DUNNING_ATTEMPTS = 3`:

1. Loads the internal Subscription row. **Idempotency guard:** if `sub.dunningAttempt >= attempt`, no-op (Stripe can fire `invoice.payment_failed` multiple times for the same retry).
2. Updates the row: `dunningAttempt = attempt`, `stripeStatus = "past_due"` (or `"canceled"` when `attempt >= MAX_DUNNING_ATTEMPTS`).
3. Picks the notification message based on attempt:
   - Attempt 1 → "Payment failed — please update your card"
   - Attempt 2 → "Payment failed again — 3 days to update"
   - Attempt 3 → "Subscription cancelled" + `status="cancelled"`
4. Fires the notification to every tenant user via `createNotification({ type: "payment_failed", sendEmail: true })`.
5. On the final attempt, also calls `stripe.subscriptions.cancel()` so Stripe stops retrying (our DB is now the source of truth — the user has to resubscribe via /billing).

**`src/lib/notifications.ts`** (modified) — added `"payment_failed"` to `NOTIFICATION_TYPES` (the closed 7-item list now has 8 — the Notification model's `type` column is just a `String` so no schema migration needed).

**`src/components/glass/notification-bell.tsx`** (modified) — added a `payment_failed` entry to `TYPE_ICON` (reuses the `AlertTriangle` rose-500 icon already used by `post_failed`).

### 3. Service Worker Fix

**`public/sw.js`** (rewritten) — bumped cache version `socialflow-v3 → socialflow-v4` and introduced a route-aware fetch handler:

- **Static assets** (JS, CSS, images, fonts) — cache-first (same as before; fast loads).
- **API routes** (`/api/*`) — network-only (never cache — always fresh; falls through to the browser's default offline behavior).
- **Authenticated routes** (`/dashboard`, `/inbox`, `/calendar`, `/composer`, `/analytics`, `/accounts`, `/campaigns`, `/media-library`, `/reports`, `/approvals`, `/team`, `/settings`, `/billing`, `/owner`, `/admin`, `/api/auth/me`, `/api/auth/logout`) — **never cached**. For HTML navigations, network-only with a 503 "You're offline" fallback response — a logged-out user can no longer see a stale snapshot of an authenticated page.
- **Public HTML pages** (`/`, `/pricing`, `/login`, `/signup`, …) — network-first with cache fallback ONLY when the network fails. Successful responses populate the cache for offline navigation.

The `activate` handler still nukes every cache whose name !== `socialflow-v4`, so the old `socialflow-v3` cache (which may contain authenticated HTML snapshots captured by the prior SW version) is purged on next SW activation. `/api/auth/logout` continues to send `Clear-Site-Data: "cache", "cookies"` to additionally clear the HTTP cache + cookies on explicit logout.

## Stage Summary

Stripe recurring billing is wired end-to-end:

- **Backend**: `createStripeSubscription` mints a Stripe `Product` + recurring `Price` + `Subscription` with `payment_behavior: "default_incomplete"`, returning the first invoice's PaymentIntent client secret for Stripe Elements. The webhook handles `invoice.paid` (records a completed Payment, generates a paid Invoice, credits the owner's BankAccount, fires the "Monthly payment received" notification, stamps `stripeStatus="active"` + `stripeCurrentPeriodEnd` on the Subscription) and `invoice.payment_failed` (records a failed Payment, hands off to the dunning module which escalates notifications over 3 attempts and cancels the subscription on the final attempt).
- **Frontend**: the /billing page shows an "Auto-renew: ON" badge (green) / "Payment past due" (amber) / "Auto-renew: OFF" (red) next to the plan name, a "Next charge: Nov 6, 2026" card pulled from `stripeCurrentPeriodEnd`, and a "Manage billing" button that opens the Stripe Customer Portal in a full-page redirect (no card details ever touch our server).
- **Dunning**: `src/lib/dunning.ts` is the single entry point for payment-failure handling — `handlePaymentFailure(subId, attempt)` is idempotent per attempt, escalates the notification ladder ("Payment failed — please update your card" → "Payment failed again — 3 days to update" → "Subscription cancelled"), and cancels the Stripe Subscription on the final attempt.
- **Service worker**: bumped to `socialflow-v4` with a route-aware fetch handler — static assets stay cache-first, API routes are network-only, authenticated HTML routes (`/dashboard`, `/inbox`, `/billing`, etc.) are never cached so a logged-out user can no longer see a stale authenticated snapshot. Old `socialflow-v3` caches (which may contain authenticated HTML from the prior SW version) are purged on next activation.
